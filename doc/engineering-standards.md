## 3. 技术选型草案与热度依据

### 3.1 首期候选组合

| 层 | 候选选择 | 理由、代价和采用条件 |
|---|---|---|
| 语言与运行时 | TypeScript `strict`；受支持的 Node.js LTS | 页面与服务契约共用一种语言；仍需运行时校验。初始化时依据 [Node 官方发布表](https://nodejs.org/en/about/previous-releases)核对状态与依赖兼容，记录具体版本 |
| Web 与服务入口 | React + Next.js App Router / Route Handlers，模块化单体 | 沿用 PRD React/Next.js 与 Node 候选，减少两个服务的部署与契约维护；需要理解服务端/客户端边界。若团队熟悉 Python 或部署限制不适合，再重审 |
| 视觉样式 | 语义化 HTML、CSS Modules、少量 CSS 变量 | 字号、颜色、间距集中管理；复杂组件出现时再评估组件库，避免重复引入样式体系 |
| 数据校验 | Zod，契约集中维护 | 校验请求与模型结果，并推导 TypeScript 类型；类型正确不等于事实正确。只保留一份字段定义，避免手写类型和校验器漂移 |
| 任务协调 | 显式状态转换 + 应用服务 | 当前流程有限，可直接审查、测试；只有确有长任务恢复、持久人工中断或复杂分支需求时，再评估 LangGraph 等工作流框架 |
| AI / OCR | 服务端 Provider 接口，供应商和模型待样本测试 | 更换模型不改页面和业务规则。未核实 StepFun 配置、视觉能力、保留策略与质量；不假定兼容某一 API 协议就具备相同能力 |
| 存储 | 本地单进程技术演示可用有期限的内存任务与私有临时文件；实际部署另行确定 | 内存实现不保证重启恢复或多实例一致。线上若需保留任务，必须先确认数据库/私有对象存储和清理方案 |
| 定向测试 | Vitest；Playwright + `@axe-core/playwright` | 单元/契约与浏览器流程分开；测试依赖仅开发使用，真实模型调用单列执行；版本需与 Node 和框架兼容 |

### 3.3 何时扩大技术栈

- 真实样本表明云端视觉提取效果、成本或数据策略不合适，且本地资源可用：再评估独立 PaddleOCR 服务；Python 部分沿用用户要求的 `uv` 工具链。
- 需要重启恢复、多个实例共享任务或可靠反馈统计：选择明确持久化方案，写数据结构、过期和访问策略，再落库；数据库尚未选定。
- 请求时限无法容纳实际处理：引入持久任务队列及 worker，不能把请求返回后的内存 Promise 当可靠后台任务。
- 出现独立部署、资源隔离或团队职责需求：再考虑拆服务。当前只在代码层隔离职责。
- 需要虚拟人、音频或批处理：先取得对应范围决定，复用任务契约和 Provider 边界，不提前建立空实现。

每次重要选型记录：问题、候选、证据、结论、取舍、验证、回滚方式和日期；不得在未经确认时把选型草案改成“已决定”。

## 4. 结构与职责边界

以下是拟议结构，只创建当前任务实际需要的部分：

```text
doc/                         本轮五份文档
src/
  app/                       页面与 HTTP 入口：参数、会话、响应
    api/v1/tasks/            任务 API，路径待接口评审
  features/accessibility/    上传、结果、核对、反馈的交互组件
  domain/                    任务状态、关键事实、确认与业务规则
  application/               用例编排、取消、清理、预算和幂等协调
    ports/                   Provider、TaskRepository 等外部依赖接口
  infrastructure/            模型、临时存储、日志等具体适配器
  contracts/                 共享 Schema 和可公开的错误契约
tests/                       定向业务、契约与浏览器测试
```

调用链：页面 → HTTP 入口 → application 用例 → domain 规则 + ports → infrastructure 适配器。组合入口负责把适配器传给用例，domain 不引用 React、Next.js、环境变量或模型 SDK。

审查要求：

- 页面不直接请求模型服务、不读取服务端密钥、不负责判断任务最终状态。
- HTTP 入口负责会话与输入检查，业务判断进入用例或 domain；限制文件体积的检查必须在完整缓冲前开始。
- Provider 只处理供应商协议与错误映射，不决定用户是否真正解决问题。
- Schema 在 contracts 定义，端点、模型解析器与界面复用；提示词集中在对应模型适配模块，带版本。
- 测试用替代 Provider 验证业务，不要求真实网络；增加第二家模型时业务规则应能复用。
- 不建立无具体用途的通用 `BaseService`、万能工具类或插件系统。抽象只表达已发生的外部边界或重复规则。

扩展验收例：更换模型适配器只影响适配器、配置与契约测试；若必须修改页面或确认逻辑，应重新检查职责分配。

## 5. 数据、任务与接口契约

### 5.1 关键字段

沿用 PRD §9.4 的逻辑字段，以下扩展是设计建议：

| 字段 | 拟议规则 |
|---|---|
| `schema_version` | 契约版本，初版候选为 `1`；不接受未知版本静默解析 |
| `task_id`、`task_type` | 不可预测的任务 ID；仅接受当前已实现的任务类型；ID 不是访问凭证 |
| `status` | 受服务端状态转换控制，模型不能直接写任务状态 |
| `original_content`、`summary` | 分别显示提取内容和 AI 整理；提取文本仍可能识别错误 |
| `key_facts` | 每项包含 `field`、`value`、`evidence`、`verification_status`；无依据的 `value` 为 null，另列不确定原因 |
| `evidence` | 关联样本或原材料中可核实的文字/位置；模型引用可能出错，需人工对照，不因存在引用就认定真实 |
| `action_steps` | 仅在已实现截图任务时返回；每步只依据可见内容，高风险情况停止并提示核实 |
| `uncertainties`、`safety_warnings` | 可为空数组；缺字段、模糊内容与风险必须用可理解文本显示 |
| `review` | 记录核对范围、人工修改与结果版本；可选项不能被界面默认勾为已核对 |
| `feedback` | 分别记录已解决、部分解决、未解决或未反馈；不能从处理成功推断已解决 |
| `created_at`、`expires_at` | 使用带时区的标准时间字符串；到期策略由应用执行，不能只显示日期 |

不使用模型自报的百分比充当“校准置信度”。当前不定义未经评估的 90% 等自动放行阈值。

### 5.2 状态与人工核对

候选主流程：`pending → processing → needs_review → completed`；另设 `failed`、`cancelled`、`expired` 终止路径。只允许服务端定义的转换，终止后拒绝晚到结果覆盖。

`needs_review` 可展示明确标记的草稿；人工核对关键字段或确认“未知”后进入 `completed`。`completed` 仅表示处理与核对流程完成。任务是否解决由 `feedback` 记录；产出是否被机构采用需要独立证据。

删除采用独立的访问与清理过程：立刻使任务不可读/不可更新，取消可取消的处理，清理本方文件与缓存。尚有供应商请求时阻止其晚到结果重新写回。用户应能了解本方删除范围及第三方留存限制。

### 5.3 HTTP 设计建议

以下均未实现，确认异步与存储策略后再定稿：

| 接口 | 职责与约束 |
|---|---|
| `POST /api/v1/tasks` | 上传一个文件和目标；校验来源、会话、体积与格式；受并发/请求预算约束 |
| `GET /api/v1/tasks/:id` | 当前会话查询状态和可读结果；跨会话不得读取，响应不进入公共缓存 |
| `POST /api/v1/tasks/:id/review` | 提交核对与修改，携带结果版本，防止覆盖新版本 |
| `POST /api/v1/tasks/:id/feedback` | 记录使用反馈，不修改原始提取事实 |
| `POST /api/v1/tasks/:id/cancel` | 请求中止；说明可能无法撤回已发出的第三方调用 |
| `DELETE /api/v1/tasks/:id` | 撤销访问并启动清理；重复删除保持安全且可解释 |

所有端点先验证会话归属；写操作验证来源并采取 CSRF 防护。匿名模式使用受保护的会话凭证，不能只凭 URL 中的 task_id 授权。线上 Cookie 使用 HttpOnly、Secure 与适当 SameSite 策略。

错误结构统一为 `{ code, message, request_id, retryable }`。候选映射：400 无效参数、413 文件过大、415 不支持类型、409 版本或幂等冲突、429 频率/预算限制、502 上游失败、504 上游超时。未知或无权限任务采用一致响应，避免泄露存在性。

创建任务支持幂等键，作用域包含会话与载荷摘要。同键同载荷复用结果，同键不同载荷返回冲突；应用服务统一控制重试，Provider 不再隐式叠加重试。多进程部署必须验证幂等与预算的共享原子性。

## 6. 无障碍与页面制作规范

依据 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 及其解释文档；下表是当前流程的重点，不是全部适用准则清单。

| 项目 / 准则 | 制作规则 | verify |
|---|---|---|
| 非文本信息 1.1.1；结构 1.3.1 | 页面声明中文语言；使用语义标题、表单和按钮；装饰图不重复朗读，信息图有等效文字 | 人工检查阅读顺序、替代文字及信息完整性 |
| 对比度 1.4.3、1.4.11 | 普通文字至少 4.5:1，大字至少 3:1；适用控件/状态视觉信息至少 3:1；不只靠颜色表示状态 | axe 与人工核对实际前景背景；[文字对比度解释](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| 缩放与重排 1.4.4、1.4.10 | 文字缩放 200% 可用；普通纵向内容在 320 CSS px 宽度可重排，不双向滚动，例外按标准处理 | 真实浏览器缩放、窄屏检查；[重排解释](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) |
| 键盘 2.1.1、2.1.2 | 上传、核对、复制、反馈和删除全部可用键盘；不设键盘陷阱 | 断开鼠标完成全流程；键盘可关闭弹窗并返回触发点 |
| 焦点 2.4.3、2.4.7、2.4.11 | 顺序合理、清晰可见、不会被固定浮层完全遮挡；更新结果不随意抢焦点 | Tab / Shift+Tab 走查成功、失败和弹窗路径 |
| 目标尺寸 2.5.8 | 依标准检查至少 24×24 CSS px 或满足间距等例外；本项目主要按钮建议至少 44×44，属于产品建议 | 设备上检查尺寸、间距和误触；[尺寸解释](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) |
| 标签与错误 2.5.3、3.3.1、3.3.2 | 可访问名称包含可见标签；错误关联具体输入，说明如何修正 | 读屏复核控件名称、错误发现与恢复 |
| 状态 4.1.2、4.1.3 | 上传、处理中、完成、失败和删除有可感知文字；恰当使用状态区域，避免频繁播报 | 读屏确认开始/结束能获知，正文不会持续打断 |

正文字号建议默认不小于 16px，这是 PRD 的产品约定，不是 WCAG 的统一硬性字号。遵循 `prefers-reduced-motion`，动画可关闭；不自动播放声音，音频必须有文字替代且可暂停。虚拟人加载失败时核心流程仍可用。

测试组合：至少一种桌面读屏方案（如 Windows NVDA + Edge/Chrome），一种移动方案（如 iOS VoiceOver + Safari 或 Android TalkBack + Chrome）。实际设备、浏览器与读屏版本、未覆盖组合在报告中列明。

Playwright 官方明确建议把自动、人工与包容性用户测试结合使用，见[无障碍测试文档](https://playwright.dev/docs/accessibility-testing)。自动检测目标为受测页面无 critical/serious 违规，其他问题逐项评审；未测页面、规则覆盖外问题与人工阻断问题都不能因自动报告为零而忽略。

## 7. 文件、隐私与模型安全

### 输入与文件

- 图片候选 JPG、PNG、WebP，单文件上限候选 10 MB；音频候选 MP3、WAV、M4A，25 MB、5 分钟。数值来自 PRD FR-002 的建议配置，仅在对应任务进入范围后启用，并服从平台/模型的更小限制。
- 服务端联合校验声明类型、扩展名、文件签名及实际解码结果；限制字节、像素/解码资源，后续音频还要限制时长。不仅依赖浏览器校验。
- 服务端生成存储名；禁止用户路径拼接；文件存放于非公开目录或私有存储。最小化元数据，不把材料路径放进公共 URL。
- 首版不接收 SVG、HTML、压缩包或任意远程 URL；扩大格式与 URL 导入前另评估解析、XSS、SSRF 等风险。
- 文件大小与格式限制、失败原因在上传前说明；可访问的错误恢复与取消入口属于主流程。

### 数据生命周期

1. 上传前说明处理目的、第三方传输和保留策略；提示不要提交密码、验证码、证件等敏感内容。
2. 只处理本任务需要的数据；密钥只在服务端，不能进入 `NEXT_PUBLIC_*`、页面、客户端 bundle 或日志。
3. 临时文件在成功、失败、取消及超时路径均安排清理，并有清理异常的可观测记录。期限与兜底清理机制在接收真实资料前确定。
4. 页面与 API 对任务资料禁用公共缓存；删除同时考虑本方源文件、派生结果、日志、备份及正在运行的请求。
5. 测试样本需有使用依据；真实用户材料不默认进入回归集、遥测或训练集。日志仅记录 request_id、任务类别、错误码、耗时、模型版本及供应商提供的用量等必要字段。
6. 公益证据与隐私策略统一设计：受控测试可保留授权样本；真实材料优先保存必要且有依据的最少记录，公开分享另行授权。哈希和匿名标记不自动消除可关联风险。

### 模型与输出

- 图片、OCR 文本、网页内容与上传音频都属于不可信资料。资料中的“忽略规则”“调用工具”等文字不能改变系统指令或用户权限。
- 首版模型只获得当前任务必要的只读分析能力；不赋予任意浏览、文件执行、付款、发消息或控制第三方应用的权限。
- 输出先做 Schema 校验，再做关键事实/风险规则检查。无法确认的时间、地点、金额、联系人用 null 与不确定说明；不能通过二次生成把缺失事实补成确定值。
- 纯文本安全渲染。需要 HTML 结果时从受控模板生成，编码不可信值；不直接执行模型给出的 HTML、脚本、链接或工具调用。
- 重要信息要求核对，高风险任务给出可理解提示；不把产品名称中的“急救”解释为医疗/紧急服务。

## 8. 注释、可维护性与去冗余

公共接口、跨模块边界和复杂分支写中文说明，标识符保留英文。注释至少解释职责、输入输出、失败、取消/超时、数据保留与设计原因中适用的部分；普通自解释代码不逐行复述。

示例仅说明注释粒度，不是已有实现：

```ts
/**
 * 提取海报中的候选事实，供后续人工核对；不宣告任务已解决。
 * 输入只包含已通过上传校验的图像引用和本任务需要的用户目标。
 * 缺少原文依据的字段返回 null，并附可理解的不确定原因。
 * 供应商超时/格式错误由适配器映射为统一错误，本层不隐式重试。
 * 调用方控制预算及取消；结果返回后仍须确认任务未被删除或终止。
 * 实现不得记录图像内容、原始提示词或服务端密钥到公共日志。
 */
interface PosterProvider {
  extract(input: PosterInput, signal: AbortSignal): Promise<PosterExtraction>;
}
```

代码审查检查：

- 先读当前模块、相关测试与规则；每一行改动都能对应需求或必要后果。
- 文件与函数按职责命名；一个模块不同时包办界面、供应商调用、数据保存和事实判断。
- 常量与配置只保留一个权威来源；共享的事实结构由 Schema 推导；状态转换集中维护。
- 同一业务规则出现真实重复时再抽取；不同业务只是外观相似时保留独立规则。
- 更新代码同时更新失效注释；不留下没有任务号和处理条件的 TODO；仅清理本次改动造成的孤儿代码。
- 新依赖写明用途、维护状态、许可和替代成本；锁文件纳入版本控制。代码、模型权重、角色素材与字体许可分别核对。
- 版本升级按兼容性和已知修复评估；不以“最新”代替评估，也不把过时的版本号写成长期规则。

## 9. 测试、有限模型评估与可观测性

| 验证层 | 最低关注内容 | 证据边界 |
|---|---|---|
| 单元 / 契约 | Schema、未知事实、非法状态转换、Provider 错误映射、提示注入样本 | 使用替代实现验证规则；不证明真实模型质量 |
| 集成 | 同键重复请求不重复计费触发；跨会话拒绝访问；取消/删除后的晚到响应；过期与清理 | 需要实际存储/服务语义；多实例使用并行独立请求验证 |
| 浏览器 | 上传→核对→反馈→删除；不支持格式、失败、超时、刷新与重复点击 | 记录真实界面与网络模式，Mock 与 live 分开 |
| 无障碍 | axe 自动检查 + 键盘、读屏、缩放人工走查 | 自动通过只能覆盖自动规则；发现阻断问题先修复 |
| 模型质量 | 固定样本与人工答案，逐字段遗漏/错误/编造，未知处理 | 保留失败样例和分母；Schema 通过不代表内容正确 |
| 用户任务 | 是否完成、耗时、额外人工帮助、关键误解、主观反馈 | 目标用户与开发者测试分开，不外推为真实公益规模 |

后续小规模模型评估的默认执行提案：

- 执行前说明本轮最多 **10 次外部模型请求**，所有重试和模型阶段合并计数；每个逻辑操作至多重试 1 次，仍受总上限约束。需要超过上限时先报告新的规模与原因。
- 只对明确可重试的临时错误退避重试；超时、状态未知且可能已经计费时，不盲目重发。尊重供应商 Retry-After，避免 SDK 与用例重试叠加。
- 默认候选单次超时 30 秒，与 PRD 15 秒性能目标分别记录；按真实接口约束调整。连接/鉴权错误、额度错误立即停止；连续两次服务失败、发现敏感资料或关键事实严重虚构时停止本轮并报告。
- 使用用户已授权的小规模 StepFun 测试条件，不逐轮重复索要费用授权；其他供应商调用遵循对应授权。未授权的真实个人数据不发送。
- 结束后报告实际请求数、失败/重试数、逐样本结果、耗时及供应商可得的输入/输出 Token；没有提供用量则写“未知”。请求上限不是人民币费用上限。

首轮测试素材建议 10 份，是待准备目标，不是已存在数据。清晰图、低清/遮挡、缺关键字段、无文字、恶意指令等都应覆盖。PRD 正确率/完成率目标要明确分母；“不知道”与错误补全分别计数，不能只在模型愿意回答的字段上计算成绩。

应用初始化后拟提供下列脚本；目前尚不存在 `package.json`，本轮没有执行：

```powershell
npm.cmd ci
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run test:unit
npm.cmd run build
npm.cmd run test:e2e
```

脚本应使用非 watch 模式；浏览器依赖安装另记。按改动风险选择定向检查，跨模块再运行相关测试、类型与构建。普通 CI 不依赖付费模型或生产密钥，真实评估单列有上限的人工触发步骤。

观测任务类型、阶段耗时、错误码与实际用量；匿名反馈和 request_id 的保留仍受数据策略约束。离线缓存演示必须标注离线/预生成，不能包装成现场实时调用。

## 10. 提交、回滚与交付要求

每个实现批次先定义完成标准，再修改、验证和提交。提交前检查工作区与暂存区，保留他人变更；一个提交对应一个可审查目的，不混入私密配置、素材原件或无关重构。

提交说明包含：触发问题与实际行为、主要改动、验证结果、未覆盖风险。每轮非简单实现补充“结构影响”：需求经过哪些层、实际改动哪些层、相关层保持原状的原因。

回滚优先通过普通反向提交或适配器/配置切换完成。若后续引入持久化数据变更，需先设计兼容性与回滚策略；不能把代码回滚当成数据恢复。禁止未经授权的强制推送或破坏性 Git 操作。

正式交付前核对：

- 功能、类型、构建及必要流程检查具有可复查记录；失败与未测范围明确。
- 真实模型、无障碍和用户测试分别报告；数字附样本、分母与环境。
- 文件访问、超时、取消、清理与删除行为和隐私告知一致。
- 赛事要求、部署平台限制、供应商条款与素材使用依据已核实。
- 发布、部署、外部消息或对外提交获得对应授权；本地提交不代表允许执行这些动作。
