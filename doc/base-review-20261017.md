## 4. 接入前需要处理的具体问题

### 4.1 运行时与容器约束尚未对齐

远端 ACC 的 Node 版本上限和平台 Node 22 镜像与本地 24+ 约定冲突。本轮只找到本机 Node `v24.13.0`；Docker Linux daemon 未运行，未做 Node 22 或平台镜像验证。

建议优先请底座方评估同系 Node 24 镜像及检测浏览器支持；若平台必须固定 Node 22，再单独做兼容性验证和必要适配。不能先更改 engine 声明来宣称兼容，也不应为接通页面而跳过 axe 或图片解码。

### 4.2 正常启动并非只读行为

demo 的 `src/server.js:9` 调用 `openDatabase()`；`src/database.js:95` 开始的逻辑在数据库不存在时尝试建库，`openDatabase()` 还会执行迁移。`npm start` 因此可能修改共享开发库。本轮仅运行已审阅的测试入口，没有正常启动 demo。

远端 ACC 使用单独的 `db:migrate` 命令；其数据模型和迁移记录与 demo 不同。二者虽然连接同一主机，也不能混用 schema 或直接运行对方迁移。

### 4.3 demo 有敏感配置兜底，不宜直接作为公开账号服务

`m-9701-demo/src/config.js:5` 存在非空、非占位的数据库密码字面量；`src/app.js:192` 在未配置会话签名密钥时使用固定字符串兜底。测试和种子账号属于演示用途，不能当作真实发布者身份已准备完成的证明。

底座方应在用于公开服务前轮换已暴露凭据、移除真实密码兜底、提供运行时密钥和明确账号来源。本文不复制密钥值；没有替用户更改凭据或重写 Git 历史。

### 4.4 同名 API 与任务状态的含义冲突

两套 ACC 都有 `POST /api/tasks`，但远端接受 `multipart/form-data`、返回处理文本；本地接受经过运行时校验的 JSON、返回需继续核对的任务。直接把 `/api` 代理过去会改变协议，不能只靠同名路由接入。

远端 `succeeded` 仅代表模型处理成功；本地 `completed` 代表本次 HTML 检测与人工确认完成。状态不能直接等同。远端 SQL 当前也没有正文、修订、检测 hash、人工确认或发布内容字段，已有“持久化”不等于结果已保存或可公开阅读。

建议在适配方案中明确独立命名空间、错误契约和状态映射，保留远端既有三类入口；具体路径和实施范围尚未定稿。

### 4.5 已用替代数据库复现：非法图片返回后任务仍处于处理中

`server/index.mjs:57-59` 先创建任务、落临时文件并保存上传元数据，`67-68` 再校验图片签名。签名失败时直接返回 400，未进入 `catch` 的失败状态写入；`finally` 仅清理上传文件及元数据状态。

本轮复制了与该 SHA 逐字节一致的 `server/index.mjs`，仅以本地替代模块提供数据库函数，提交 MIME 为 PNG、签名无效的合成字节。实际返回 400；记录的调用依次是 `createTask`、`recordUpload`、`finishUpload:deleted`，没有 `finishTask`，替代数据库任务状态仍为 `processing`。外部请求尝试为 0。

这确认了应用控制流中的状态遗漏，不能代替真实 MySQL 或线上故障复现。既有 3 项测试未覆盖该路径。建议负责远端服务的一方前置签名校验或显式保存失败状态，并补定向回归；本轮未修改远端业务代码。复现脚本为 `.local/validation/base-review-20261017/repro-invalid-image.mjs`，原始输出为同目录 `invalid-image-repro.json`。

### 4.6 代码推送可能也是部署动作

官方 Flow 支持代码提交、Tag、合并请求等事件与分支/路径过滤，见 [代码源触发说明](https://help.aliyun.com/zh/yunxiao/user-guide/code-source-trigger)。这只能说明平台能力，不能证明本项目已启用哪些规则。

目前仅有列表页地址，没有项目的具体流水线或 YAML。远端 ACC README 写 Linux 流水线使用 `yarn install`，但本轮树中只有 `package-lock.json`，没有 `yarn.lock`。实际依赖锁定、构建步骤、初始化脚本、目标镜像和触发分支均需与底座方核对。未核实前，不把“只 push 代码”当成与部署无关的动作。

## 5. 建议拆成三次可验收的交接

| 交接包 | 负责范围 | 输入与完成标准 |
|---|---|---|
| A：底座运行契约 | 底座方提供环境、账号、流水线约束；AI 整理验证 | 选定 Node 版本与镜像、浏览器运行条件、应用端口、Linux 依赖安装命令、实际流水线 ID/代码源/触发分支、开发 schema、发布者身份来源 → verify：在隔离开发环境按同一版本跑通合成用例 |
| B：业务链路适配 | AI 实现已确认范围；用户验收产品路径 | 对齐命名空间、输入输出、会话和身份边界；保留角色 → 科普 → 海报 → 修改/检测/确认 → 反馈 → verify：原业务与浏览器回归通过；不同会话隔离，修改使旧检测失效 |
| C：主动发布闭环 | 用户决定公开内容与保留规则；AI 实现；底座方提供持久化/部署能力 | 发布预览与独立授权、存储确认版本、匿名公开阅读、发布者撤回 → verify：第二个浏览器能读公开副本但不能管理他人发布；原任务到期后仍可撤回；内容变化后重新检测确认 |

这是建议分工，尚未向底座提供方发送或取得对方承诺。公开功能保留 [10/16 方案第 6 节](base-handoff-and-integration-20261016.md#6-公开结果本轮准备的最小产品约定) 的约束：原图与完整回执不默认公开，实际公开 HTML 必须与检测对象一致，任务删除和发布撤回分别说明。

账号建议仅在发布/撤回时建立可靠归属，基础海报任务仍可匿名体验；这是待审阅设计，不能把 demo 登录态或反馈凭证直接当成已打通的账号系统。
