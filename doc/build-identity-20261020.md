## 复现、修复与验收

1. 先复现 → verify：隔离目录中的实际服务保持应用文件不变，只改变构建日期 / 提交号，旧代码仍报告需要重启。初始定向结果 1 通过 / 3 失败，分别显示缺少内容指纹、元数据差异误报及未识别指纹变化，记录在 `.local/validation/build-identity-20261020/before.tap`。
2. 按内容标识 → verify：构建完成后生成 applicationHash，覆盖全部 dist 文件路径 / 字节、package.json、锁文件及 Node 版本；排除自引用的 build-info.json，Git 提交号、dirty 与时间仍独立保留溯源。相同内容重复构建指纹一致；后端、CSS、本地素材、锁文件改变指纹。它比较完成构建，不是依赖审计或任意文件篡改检测。
3. 服务判断 → verify：启动时固定运行构建，后续只读可用记录。两边指纹有效时比较指纹；旧记录缺少指纹、损坏、缺失或不合法时为未知，不能仅凭提交号 / 时间宣布一致。字段为可选增量，页面仍沿用现有 true / false / null 提示，不自动重启、清空任务或改变检测确认。
4. 相关验证 → verify：独立无密钥 / 无素材工作区类型、构建、**64 项业务及 6 项相关浏览器检查通过**，0 浏览器跳过 / 意外失败 / flaky。浏览器覆盖版本提示、未知退路、草稿保留和任务读取恢复。没有重复运行无关浏览器集合，也不把旧结果与新通过数累加。
5. 本机加载 → verify：单独提交后构建干净版本，沿用既有清空临时任务 / 本地重启授权，核验所拥有旧进程及未消费的请求预算。再在实际合成任务存在时重复构建同内容，检查不要求重启、任务 / revision / 原到期时间保留，随后完成实际检测、确认、三类导出和删除。此项尚待执行，不提前写成通过。
