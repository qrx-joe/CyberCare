## 3. 协作方式：按可验收的小功能交接

“底座提供方出选型与工程基础，接手方实现业务，遇到落地问题再反馈”可以试行。需要补充的是：交接单位、问题归属、验收人和回滚点。否则容易反复传整仓，环境问题和产品判断混在一起。

| 角色 | 建议负责 | 交付依据 |
|---|---|---|
| 底座提供方 | 说明选型取舍、跑通原始工程、环境/数据库/鉴权/部署约束，处理底座问题 | 指定版本、启动步骤、脱敏配置样例、初始化方式、最小示例 |

| AI 工程协作 | 读代码、提出异议、实现已确认业务、补必要测试、定位阻塞 | 小范围 diff、运行证据、失败事实、结构影响和交接说明 |
| 双方共同讨论 | 业务与底座约束冲突、公开发布、数据保留、身份与权限 | 先给证据与取舍，再形成决定；建议不自动变成已批准方案 |

1. **定位工程与版本** → verify：根目录及更近的 AGENTS、README、依赖锁、目录职责、分支与 SHA；先看安装/启动脚本，记录已有修改。
2. **恢复运行入口** → verify：原始示例能按文档启动，前后端端口和构建产物明确；未审查前不运行初始化或迁移脚本。
3. **恢复调用与数据流** → verify：页面 → API → 鉴权/租户 → 业务 → 存储/模型的实际代码路径，明确错误响应与契约。
4. **核实存储与环境** → verify：数据库版本、schema/迁移来源、是否独享开发库、最小权限和回滚方法；源码与现有文档可先审阅，真实共享库操作另行确认。
5. **核实接入和运行条件** → verify：Node/浏览器支持、同源路由、静态素材路径、HTTPS、会话和模型限制；不能靠关闭现有安全校验来接通。
6. **给出接手结论** → verify：区分“可原样接入 / 需要适配 / 阻断”，逐项给文件证据与最小验证结果，再确定实施 diff。

## 5. 接入路线与完成标准

1. **确认底座能力和双方约定** → verify：完成上一节的代码审查，锁定基线版本；公开语义已由用户确认，身份、存储与运行条件仍需代码证据。
2. **做最小接入验证** → verify：若底座支持代理独立 Node 服务，先验证同源页面与 API；若要求在底座内部运行，再给出适配层方案。运行合成海报原闭环，避免一开始重写业务层。
3. **确定发布契约与数据生命周期** → verify：发布对象、归属、撤回权限、保留期限、失败行为可逐条验收；适配底座现有能力，不并行自造一套账号体系。
4. **在隔离开发环境实现发布闭环** → verify：授权后迁移到独享开发库，用合成数据验证主动发布、无登录阅读和发布者撤回；底座无所需能力时先提出最小补充方案。
5. **回归、审查和回滚演练** → verify：类型/业务/构建/浏览器检查；原任务与公开副本隔离、跨用户拒绝访问管理接口、撤回链接失效。交付可审查版本后再决定公开部署。

若底座不能支持 Node 服务或检测浏览器，先汇报证据和替代方案，不能用固定样例代替检测或真实模型行为。若引入跨模块重构、生产依赖或破坏性 API 变更，先形成具体 diff 范围与取舍。

## 6. 公开结果：本轮准备的最小产品约定

下面除“用户主动发布后，大家能查看已确认结果”外，均为待审阅的实现建议，尚未实施。

### 用户路径与发布门禁

保持现有产品路径：角色求注意力 → 预设互动/短科普 → 海报任务 → 检测与逐项确认 → 角色反馈。在核对完成后增加可选发布入口，先预览完整公开内容并确认公开范围。

“有权处理原材料”“内容已核对”“同意公开结果”是三个不同动作。默认不发布；勾选处理权限或完成核对均不应自动发布。发布前检查归属、当前状态、revision、检测 hash 和逐项确认；重复点击同一发布请求须幂等。

### 公开对象与隐私边界

建议第一版仅提供独立公开阅读链接，暂不默认建设可浏览全部投稿的广场、搜索或排名。“所有人可通过链接阅读”与“进入公开目录”是不同范围，目录需求仍待确认。

建议持久化一份发布者审阅过的最小公开副本：可读文字、受控 HTML、必要的模式/未知提示、发布与修订信息。管理用的 owner、source revision、内容 hash 和撤回状态保留在服务端。原图、任务会话、文件名、内部修改记录、模型用量和完整回执不默认公开。正文自身也可能包含联系方式等信息，公开预览必须覆盖全部将发布的文本；不能仅靠字段白名单声称已去除个人信息。

当前 `renderText()` / `renderHtml()` 包含完整转录、来源备注及不确定项，`receipt` 还包含内部处理记录，不能直接把现有下载接口变成公开接口。若公开模板或内容有变化，必须对**实际公开版本**重新检测并确认，不能沿用不同 HTML 的检测结论。

### 生命周期与撤回

- 原任务与图片继续遵守当前 30 分钟临时处理规则；公开副本需要独立生命周期。页面应在发布前说明：任务到期不会自动撤回已发布副本。
- 发布结果建议绑定底座已有账号/租户的发布者身份。发布和撤回 API 都检查归属；若底座无身份能力，匿名发布后的可靠撤回方案仍待决定，不先实现无法管理的永久公开内容。
- 公开副本发布后冻结内容；修改应重新生成版本、检测、确认和发布，不悄悄改变他人已查看的内容。
- 发布者应能在原任务到期后继续撤回公开副本；撤回后旧链接不可读，缓存策略需支持撤回。已被他人复制或下载的内容无法由网站保证收回。
- 删除任务与撤回发布分别呈现，不能让“删除临时任务”暗示已撤回公开副本。具体保留期限、备份清理、撤回元数据保留和异常内容处理责任尚待决定。
- 仅有进程级模型请求上限不足以作为线上全局用量策略；公开服务的限流、账户预算和多实例约束需在部署前明确。

### 拟议接口边界

接口名称用于准备讨论，不能当成底座已有 API 或已批准的公共协议：

| 动作 | 拟议职责 | 关键检查 |
|---|---|---|
| 主动发布 | 从已确认任务生成独立公开副本 | 当前归属、版本、公开内容预览与授权、同份 HTML 检测、幂等；失败不产生半成品链接 |
| 公开阅读 | 匿名读取已发布副本 | 仅返回允许公开的内容；不暴露内部任务或管理数据；未发布/已撤回不可读 |
| 撤回 | 发布者撤回自己发布的副本 | 身份归属、重复撤回幂等；任务到期后仍可执行 |

持久化优先复用底座已有机制；是否用 MySQL、具体表结构和迁移脚本，待源码审查后确定。本轮未建立数据库连接或生成针对未知 schema 的 SQL。

### 发布闭环验收

1. 未确认、检测失败、版本/hash 过期、未授权公开或他人任务均不能发布。
2. 公开预览与实际公开内容一致；内容/模板变化后重新检测与确认；未知不被补成事实。
3. 同一发布请求重复提交得到同一结果；存储失败不出现可访问的半成品副本。
4. 第二个独立浏览器会话能访问公开链接，但不能读取原任务、回执或撤回他人发布。
5. 原任务到期后，公开副本按已说明的规则工作，发布者仍能撤回；撤回后旧链接失效。
6. 公开页键盘、缩放、移动阅读和实际 HTML 检测通过必要检查；axe 失败与 incomplete 如实呈现。
7. 验证只使用合成或明确授权素材；样例、人工整理和真实模型结果标识保留，不把发布次数包装为公益效果。
